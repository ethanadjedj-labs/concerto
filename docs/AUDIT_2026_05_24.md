## 6. Decision Proposal: **OUT-OF-STACK**

### Verdict
Concerto is, and should remain, **architecturally standalone**. The in-stack vs out-of-stack question is already answered by the code: there are zero Python imports between concerto and the ecosystem. The question is really about whether to formalize that independence or push toward integration.

### Why OUT-OF-STACK

**Evidence from the code:**
1. Zero imports from `arsenal`, `cortex`, `strandedgrid`, or any shared brick
2. Self-contained provisioning, email, DB, auth, billing — entire product in one repo
3. The 4 MANAGER_STATE reads are already soft (path strings, could fail silently)
4. The shared `/etc/cortex/env` is a deployment convenience, not an architectural dependency

**Product logic:**
5. Concerto is sold separately (`concerto.run`), has its own Stripe account/keys, own domain, own NF project, own DB
6. Concerto IS a development environment product — it competes with / complements the cortex ecosystem rather than being a component of it
7. Adding tight coupling (arsenal email bricks, cortex DB, cortex MCP bridge) would mean customer provisioning failures could cascade from cortex failures — unacceptable for a commercial product

**Operational evidence:**
8. The NF containers run entirely without cortex — the `mcp_server.py` inside them only calls back to `api.concerto.run`
9. Cortex's role is purely orchestration-layer (session management, state tracking) — not product logic

### What IN-STACK would require (and why it's not worth it)
- Refactor `transactional.py` to use arsenal's email sending
- Move `concerto_buyers` into cortex's DB or add a cross-DB bridge
- Wire `concerto_build` to use cortex MANAGER_STATE as source of truth (partially done, but as a read)
- Replace `/etc/cortex/env` with a shared secrets vault

This is 2-4 sessions of work for no user-facing improvement. The product already works independently.

### What OUT-OF-STACK looks like concretely

1. **Keep** cortex as the orchestration layer for sessions (inbox events, state tracking, session spawning) — this is not coupling, it's management plane separation
2. **Fix** the env file split: `/etc/concerto/env` for concerto-specific keys, symlinked or copied from `/etc/cortex/env` for shared keys (RESEND, DO tokens)
3. **Remove or harden** the 4 MANAGER_STATE reads in the backend: wrap in `try/except` with empty fallback. The customer-facing `mcp_server.py` can keep its MANAGER_STATE integration (it's a feature, not a coupling)
4. **Establish** `/root/concerto` as the single canonical source with a real deploy script (`deploy.sh` already exists) that syncs to `/opt/concerto`
5. **No separate VPS yet** — at 0 customers, sharing the empire VPS is fine. Revisit at 10+ customers
